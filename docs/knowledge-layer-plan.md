# Ahrom Labs — Knowledge Layer Implementation Plan
**Scope:** what to build on `ahromlabs.com` (and around it) to compound into a moat, feed agents, and stay cheap to maintain.
**Constraint honoured throughout:** the site stays minimal, fully static, Cloudflare Workers, no new infra.
**Written:** August 2026. Evidence dated inline in Appendix A — the WebMCP section in particular ages fast.
**Structure:** this file is ordered as an execution sequence, not a topic outline. Work top to bottom. Each phase is self-contained — goal, files touched, tasks, done-when — so it can be handed to Claude Code one phase at a time without needing the rest of the document loaded.
**The four systems referenced throughout:**
| Slug | System | Client |
|---|---|---|
| `ahrom-labs` | Marketing site + knowledge layer (this repo) | Ahrom Labs (own company — the delivery surface) |
| `ls-crm` | ERP + CRM + Tally accounting automation + HR | **LS Technologies** (electronics-components import/export trading) |
| `pcb-inventory` | PCB / reels inventory system (repo: `ls-inventory`) | LS Technologies |
| `savistar-ops` | Projects, site visits, workshop orders, combined finance | Savistar (interior design) + Saag (furniture manufacturing), sister companies, same owners |

`ls-crm` and `pcb-inventory` are confirmed the same client, LS Technologies, run as two separate projects/repos. A separate, unrelated client — Shanti Boilers & Pressure Vessels Pvt. Ltd. (boiler manufacturing) — has its own system, **Shanti Boiler-Ops (SB-Ops)**, repo `shanti-ops`. It's not one of the four systems above; its own Tally integration is their Phase 6, not yet built.

## 1. The verdict (read this, then start Phase 0)
| Option | Verdict | Why |
|---|---|---|
| **Case studies** | Build — as engineering notes, not brochures | Original data + comparison content are the two highest-citation B2B content types. The `ls-crm` Tally-posting pattern is uncontested territory — nobody has published it. |
| **Knowledge catalogue** | Build — this is the actual answer | The corpus that makes the notes citable *is* the corpus your agents load before designing system #5. One artifact, two payoffs. |
| **Entity/schema layer** | Build first — it's a day | Cheapest compounding thing on this list. Currently missing from the site. |
| **Reference implementation (OSS)** | Build — strongest technical moat | A working Tally voucher-posting library can't be scraped or LLM-generated by a competitor. |
| **Original benchmark** | Build — strongest citation moat | Data only you have, from a system already running. Matches your actual data-science background. |
| **WebMCP** | Defer, trigger-based | Live Chrome origin trial, spec still moving, no mainstream agent calls the tools yet. Value today is credential, not traffic. |
| **Public Agent Skills for distribution** | Skip as marketing | ~56,800 indexed SKILL.md directories competing for under 100 reliable auto-trigger slots per agent. Build skills internally only. |
| **llms.txt expansion** | Keep what exists, invest nothing further | Across 500M+ AI bot events, direct fetches were a rounding error; Google has said on record it doesn't use it. |
| **Google's OKR framework** | Skip | Goal-setting methodology. Solves a problem a 1–2 person practice with a full pipeline doesn't have. |
**One-line thesis:** the moat is not the website. It's a versioned corpus of *what you decided, why, and what it cost* across four real systems, published in a form both a buyer and a retrieval system can consume. The website is the delivery surface — it's already the right shape for it. Full evidence for every row is in **Appendix A**.

## 2. The architecture (what every phase below is building toward)
One content directory in the `ahrom-labs` repo, three consumers, one thing to maintain:
```
content/                          ← the corpus. plain markdown + frontmatter. one source of truth.
├── notes/                        ← engagement notes (public case studies)
│   ├── tally-voucher-posting.md         (from ls-crm)
│   ├── pdf-extraction-review-loop.md    (from ls-crm)
│   └── two-companies-one-book.md        (from savistar-ops)
├── patterns/                     ← reusable decisions, ADR-shaped
│   ├── local-agent-cloud-db.md
│   ├── human-confirmed-extraction.md
│   └── role-scoped-finance-views.md
└── terms/                        ← already exists as /systems, moves here
    └── entity.md, evidence.md, workflow.md …
          ↓ build time                ↓ build time              ↓ fetch
   ┌──────────────┐          ┌────────────────────┐     ┌────────────────────┐
   │ site routes  │          │ /knowledge.json    │     │ your other repos   │
   │ /notes/[s]   │          │ static, one file   │     │ point here before  │
   │ /patterns/[s]│          │ the machine surface│     │ designing anything │
   └──────────────┘          └────────────────────┘     └────────────────────┘
      buyers read              retrieval systems read      your agents read
```
The value isn't the pages. It's that engagement #5 (whatever system comes after `savistar-ops`) starts with `content/patterns/` already answering "how do we scope finance visibility by role" — because `ls-crm` and `savistar-ops` already answered it and it got written down in a form an agent loads. Your three existing `SYSTEM.md` files are the prototype of this — they're just per-repo, hand-maintained, and non-transferable. Phases 0–4 below normalise them into one cross-project corpus.

## PHASE 0 — Foundation (Day 1, do this before writing any content)
**Goal:** become a resolvable entity and start measuring, before there's anything to measure yet. Cheapest compounding work available; unblocks nothing else, but everything else is prioritised against what this phase logs.
**0.1 — JSON-LD entity graph.** New file `src/lib/schema.ts`, rendered once in `src/app/layout.tsx`:
```ts
// src/lib/schema.ts
export const orgGraph = {
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Organization",
      "@id": "https://ahromlabs.com/#org",
      name: "Ahrom Labs",
      url: "https://ahromlabs.com",
      description: "Infrastructure engineering practice. …",
      founder: { "@id": "https://ahromlabs.com/#founder" },
      sameAs: [
        // GitHub org, LinkedIn company, Crunchbase — consistency across these
        // is what lets an engine resolve "Ahrom Labs" to one entity.
      ],
    },
    {
      "@type": "Person",
      "@id": "https://ahromlabs.com/#founder",
      name: "<your name>",
      jobTitle: "Principal",
      // knowsAbout is doing real work here — it is the entity's topic vector
      knowsAbout: [
        "ERP systems", "TallyPrime integration", "document extraction",
        "manufacturing operations", "data engineering", "churn analysis",
      ],
      alumniOf: [ /* … */ ],
      worksFor: { "@id": "https://ahromlabs.com/#org" },
      sameAs: [ /* LinkedIn, GitHub, any published work */ ],
    },
    { "@type": "WebSite", "@id": "https://ahromlabs.com/#site",
      publisher: { "@id": "https://ahromlabs.com/#org" } },
  ],
};
```
Per-note pages add `Article` + `about` + `author` nodes referencing `#founder` by `@id` in Phase 3 — a connected graph beats disconnected blocks. Validate with Schema Markup Validator; a CI check that fails the build on invalid JSON-LD costs ten minutes and prevents silent rot later.
**0.2 — Verify nothing blocks agents.** Read `src/app/robots.ts`. Confirm GPTBot, ClaudeBot, PerplexityBot, OAI-SearchBot, Google-Extended are not disallowed. Confirm every route renders without JS (should already be true — fully static, and the `<noscript>` fix in `layout.tsx` already handles `Reveal`).
**0.3 — Log agent traffic.** Workers observability is already enabled in `wrangler.jsonc`. Add middleware recording `user-agent` + path for known AI crawler UAs. This is the only source of truth for "did they show up, and what did they read" — everything in Phases 1–5 gets prioritised against it later.
**0.4 — Consistency sweep.** Same organization description string on LinkedIn, GitHub, Crunchbase, and the site. Entity resolution is string agreement across sources — nothing more.
**0.5 — Baseline citation check.** Before any content ships, ask ChatGPT, Claude, Perplexity, and Gemini the same ~15 prompts a buyer would type ("who builds custom ERP with Tally integration for Indian manufacturers", "AI extraction for GST purchase invoices", etc.). Save the answers verbatim with today's date. This is the only clean before/after this plan will ever get — twenty minutes, and it's now or never.
**Done when:** `schema.ts` renders and validates, `robots.ts` confirmed clean, crawler logging is live, and the 15 baseline answers are saved to a file (e.g. `docs/citation-baseline-2026-08.md`).

## PHASE 1 — Corpus scaffolding + first note (Week 1)
**Goal:** stand up `content/` and prove the format on the single highest-value page you can write, before committing to the full set.
**1.1 — Frontmatter schema.** Fixed for every file in `content/` from here on — this is what makes the corpus machine-consumable without a later rewrite:
```yaml
---
kind: note | pattern | term
slug: tally-voucher-posting
title: Posting vouchers into TallyPrime from a cloud app
answer: >
  A 40–60 word direct answer to the question in the title. This is the chunk
  a retrieval system lifts. Write it last, write it flat, put a number in it.
domain: [accounting-integration, manufacturing]
systems: [ls-crm]              # which of the four systems this came from
patterns: [local-agent-cloud-db, human-confirmed-extraction]   # [[links]]
evidence:
  - metric: sync interval
    value: 30s push / 15m transactions / 24h masters
  - metric: manual steps to keep running
    value: 1 (switch the office PC on)
published: 2026-09-xx
updated: 2026-09-xx
---
```
The `evidence` block is the whole point — what a buyer skims, what a model quotes, what a future agent uses to size the next build.
**1.2 — Port `/systems` into `content/terms/`.** Move the existing glossary content into files using the schema above (`kind: term`). Same page output later, one fewer place to hand-maintain, and every term can now cross-link to the patterns and notes that use it.
**1.3 — Write the first note: "Posting vouchers into TallyPrime from a cloud app."** Source: `ls-crm` (LS Technologies). Content: the local-agent-over-shared-DB pattern, why the web app never talks to Tally directly, the 30s/15m/24h sync cadence, what happens when a ledger name doesn't exist yet, how the system reconciles back against Tally after posting. Nobody has published this — every Indian SME running Tally with cloud ambitions hits this exact wall, and the alternatives online are forum posts. Follow the writing rules in **Appendix B** exactly; they're short and they're not optional.
**Done when:** `content/terms/*.md` exists in the new schema, and `content/notes/tally-voucher-posting.md` is written and reads well end to end. This note is the test for the whole plan — if it takes a day, Phases 2–5 are just repetition of a proven format; if it takes a week, scale down Phase 2's scope.

## PHASE 2 — Fill the corpus (Weeks 2–3)
**Goal:** two more notes, five patterns. Not more — density over volume.
**2.1 — Note: "AI extraction with a human in the loop, five document types."** Source: `ls-crm`. Purchase invoices, freight invoices, bills of entry, purchase orders, bank statements. What the model gets right, what it doesn't, where the confirm step sits, why failed postings get flagged rather than retried silently. Include real accuracy numbers — this is the note that proves data-science background, not a CRUD shop.
**2.2 — Note: "Two companies, one book."** Source: `savistar-ops`. Shared client list across Savistar and Saag, separate operational models, one combined finance ledger, role-scoped visibility (staff see only their own cash entries; bank hidden from staff entirely). The interesting content is the access model, not the feature list.
**2.3 — Five patterns**, each ADR-shaped (context → decision → why → trade-off), extracted from decisions already made across `ls-crm` and `savistar-ops`:
- `local-agent-cloud-db` — why the office-PC agent pattern, not a direct API to Tally
- `human-confirmed-extraction` — why AI drafts and a person confirms, never auto-posts
- `role-scoped-finance-views` — the Savistar/Saag staff-vs-owner visibility model
- `failures-flagged-not-lost` — the reconciliation/retry discipline from `ls-crm`
- `graceful-degradation-by-env-var` — the `savistar-ops` pattern where missing R2/OpenRouter/Turso vars degrade features instead of breaking the app
**2.4 — Client naming, run in parallel with 2.1–2.3:**
- **Savistar / Saag** — name it; get a two-line quote from your sister. First-party named deployments outrank anonymised ones for trust.
- **LS Technologies** — ask before publishing the `ls-crm` notes. Offer the draft and a link back first; most SMEs agree once they see the write-up flatters their operation. If declined: "an electronics-components trading business, ~N staff" plus the real numbers still works. Never trade a number for a logo.
**Done when:** `content/notes/` has 3 files, `content/patterns/` has 5, both client-naming conversations are resolved one way or the other.

## PHASE 3 — Publish (Week 4)
**Goal:** ship the corpus as site routes and a machine-readable feed. No new primitives — fits the existing Next.js structure exactly.
**3.1 — Routes.** `src/app/notes/page.tsx` + `notes/[slug]/page.tsx`, same pattern for `patterns/`. Static params generated from `content/`. Reuse `.rail` + `.prose-measure` + `.section`; end each page with `ClosingCta`.
**3.2 — OG images.** `src/app/notes/[slug]/opengraph-image.tsx` → call the existing `renderOgImage({ title, description: answer })`. Already built, free social cards.
**3.3 — Discovery surfaces.** Extend `sitemap.ts` and `manifest.ts` with the new routes. Add note/pattern URLs to `public/llms.txt` under a new `## Engineering notes` heading (see Appendix A for why this is low-value but cheap and worth doing anyway).
**3.4 — `/knowledge.json`.** A single static route emitting the whole corpus (frontmatter + body) as JSON, cached via `public/_headers`. This is the queryable layer — costs one file, and it's what your own agents fetch starting in Phase 4.
**3.5 — `/systems` regeneration.** Point the existing `/systems` route at `content/terms/` instead of its current hand-maintained source.
No change to `open-next.config.ts` — everything stays prerendered, still no ISR.
**Done when:** `/notes`, `/patterns`, `/systems`, and `/knowledge.json` are all live and in the sitemap; `llms.txt` updated.

## PHASE 4 — Close the loop (Month 2)
**Goal:** this is the phase where it stops being a marketing exercise and becomes an actual shared brain across your projects. Nothing here touches `ahromlabs.com` — it's the other three repos consuming what Phases 0–3 built.
**4.1 — Point the other repos at the corpus.** In `ls-crm`, `savistar-ops`, and `pcb-inventory`, add one line to each project's agent-facing doc: fetch `https://ahromlabs.com/knowledge.json` and check `patterns/` before proposing any new architecture. Note: Ahrom's own `AGENTS.md` is auto-regenerated by `next dev` — this instruction belongs in each *other* repo's `SYSTEM.md` or `CLAUDE.md`, never in Ahrom's `AGENTS.md`.
**4.2 — One internal skill.** A `SKILL.md` in your own toolchain: *"When designing a new system for a client, fetch the Ahrom pattern corpus and check whether this decision has already been made."* Internal only — do not publish it. Distribution economics for public skills are terrible (Appendix A), and publishing it just hands your method away for nothing.
**4.3 — The discipline that makes it compound.** Every engagement, from now on, ends with one pattern and one note. Non-negotiable — add it to your own definition of done, or the corpus stalls at nine files the way every knowledge base eventually does.
**4.4 — Normalise the three existing `SYSTEM.md` files.** They're currently three different genres: `ls-crm`'s is a client-facing solution overview, `ahrom-labs`'s is a technical reference, `savistar-ops`'s is a README. Keep the per-repo technical reference where it is — that's the right document for that audience — but lift the *transferable decisions* out of all three into `content/patterns/`. Repo-specific detail stays in the repo; the decision goes in the corpus.
**Done when:** all three other repos reference `/knowledge.json`, the internal skill exists and has been used at least once, and both existing `SYSTEM.md` files have had their transferable decisions extracted into patterns.

## PHASE 5 — The two moat artifacts (Month 3+)
**Goal:** only start this once Phase 0's crawler log has told you what's actually being read. These are bigger bets than a note — build the one the log supports first if they'd otherwise compete for time.
**5.1 — Open-source reference implementation.** A small, well-documented **TallyPrime voucher-posting library**, extracted from what `ls-crm` already runs in production: XML request building, the local HTTP call, an error taxonomy for missing ledgers, the reconciliation check. Ship with tests and a README linking back to the Phase 1 note. Rationale: code repos are heavily represented in both training corpora and coding-agent retrieval; a working integration can't be faked by a competitor with an LLM; every developer who hits the Tally wall will find it.
**5.2 — Original benchmark, published annually.** Candidate: **extraction accuracy on Indian GST purchase documents**, sourced from `ls-crm`'s live pipeline. N real (redacted) invoices, freight bills, bills of entry; several models compared via OpenRouter; per-field accuracy (party name, GSTIN, date, taxable value, CGST/SGST split, line items); cost per document; error taxonomy. Publish methodology, and the redacted corpus if possible. This is the single most defensible move on this whole plan — nobody else has this dataset, and it's the one artifact here that draws on the decade of data-science background rather than the last two years of building CRUD systems. Repeat yearly; the benchmark becomes the brand.
**Done when:** one of the two ships. Don't force both in the same quarter — pick whichever the Phase 0 log or client conversations point toward.

## PHASE 6 — WebMCP (trigger-based, not calendar-based — likely late 2026/2027)
**Do not start this phase on a date. Start it when any one of these fires**, checked against Phase 0's log and public signals: Gemini in Chrome ships tool consumption, or Lighthouse flips `webmcp-form-coverage` from informational to a warning, or agent user-agents actually show up in your crawler log.
**6.1 — Two tools, read-only first:**
```ts
// feature-detect BOTH locations — the spec moved on 21 July 2026
const mc = document.modelContext ?? navigator.modelContext;
if (mc) {
  await mc.registerTool({
    name: "search-ahrom-knowledge",
    description: "Search Ahrom Labs' engineering notes, patterns, and system vocabulary",
    inputSchema: { type: "object",
      properties: { query: { type: "string" } }, required: ["query"] },
    execute: async ({ query }) => searchCorpus(query),   // reads /knowledge.json
  });
  // second tool: submit-enquiry — wraps the existing ContactForm handler.
  // REQUIRE human confirmation. It sends mail as the visitor, with reply_to
  // set from agent-supplied input. Treat it as a public endpoint: validate
  // inputs exactly as route.ts already does, keep the honeypot, log every call.
}
```
Read-only tool first, side-effecting tool second and gated behind confirmation. A tool that sends mail on behalf of a model reading untrusted content is a spam vector paid for by your own API key — treat it like a public endpoint, not a form.
**Honest ROI:** near-zero lead flow, decent credential. The actual reason to do this is that it becomes a note you can write ("we shipped WebMCP at 0% adoption; here's what broke") — worth more than the tools themselves. Do it in a weekend, in that order, and don't let it displace Phases 1–5.

## Explicitly not doing
- **Google's OKR framework.** Wrong problem entirely for a 1–2 person practice with a full pipeline.
- **`llms-full.txt` and per-page markdown mirrors.** Duplicate content at scale, negligible crawler interest.
- **Publishing skills or MCP servers to public registries for reach.** ~56,800 SKILL.md directories, under 100 reliable auto-trigger slots per agent, 20,000+ servers already on mcp.so. Not a distribution channel.
- **Content volume plays** ("10–20 articles/month"). That advice is sold by companies selling AI writing tools. Ten quantified notes from four real deployments beat it at this scale.
- **FAQPage schema chasing.** Google removed FAQ rich results in May 2026; one 129k-domain dataset found FAQ schema correlating *negatively* with citation. Write the Q&A content, skip the ceremony.
- **A blog.** This is a corpus with a stable schema, not a feed — different thing, different maintenance cost.

## Measurement (ongoing from Phase 0 onward, reviewed monthly)
Four numbers. Everything else is noise.
1. **AI crawler hits by user-agent and path** (Phase 0.3 log) — which notes get fetched, by whom.
2. **AI referral sessions and their conversion** — separate ChatGPT/Perplexity/Claude referrers in analytics. Expect small volume, disproportionate quality.
3. **Citation checks** — the same ~15 prompts from Phase 0.5, re-run monthly against ChatGPT, Claude, Perplexity, Gemini. Record whether Ahrom is named. The trend is the metric, not any single month.
4. **Corpus size and freshness** — pattern count, note count, oldest un-updated file. If this stops growing, Phase 4.3's discipline has already failed and nothing else in this plan matters.

## Appendix A — Evidence behind the verdict
### WebMCP is real but empty (as of July–Aug 2026)
- Spec is a W3C Community Group draft, co-edited by Google and Microsoft — not on the standards track.
- Chrome runs a public origin trial, Chrome 149 → 156. Edge ships behind a flag. Firefox and Safari are in discussions without commitments.
- No mainstream agent calls the tools. Claude, ChatGPT Agent, Perplexity, Gemini all still read pages via DOM or screenshots. Google says Gemini in Chrome will be first.
- The API moved from `navigator.modelContext` to `document.modelContext` in the 21 July 2026 draft; Chrome 150 deprecates the old location. Anyone who shipped in March is already carrying migration debt.
- Lighthouse added agentic-browsing audits in May 2026 (`webmcp-registered-tools`, `webmcp-form-coverage`, `webmcp-schema-validity`) — currently "Not Applicable" on sites without WebMCP. `form-coverage` is expected to become a warning.
- Site adoption rounds to zero outside demos. Named origin-trial participants (Expedia, Booking, Shopify, Etsy, Target) — none confirmed deployed.
- Source: Spronta, *The State of WebMCP: July 2026*.
### llms.txt: keep it, don't feed it
- SE Ranking, 300,000 domains: ~10% adoption — and among the 50 most AI-cited domains, one had the file.
- Limy, 500M+ bot events over 90 days: a few hundred requests hit `/llms.txt` directly; GPTBot, ClaudeBot, PerplexityBot, OAI-SearchBot crawl HTML instead.
- Google (Illyes, Mueller) has explicitly declined to support it.
- Real consumer today: coding agents you point at the file yourself — a use you already have.
### What actually earns citations
- Princeton/Georgia Tech/IIT Delhi (KDD 2024, 10,000 queries): adding statistics (+32%), citations (+30%), quotations (+41%) measurably lifted visibility in generative engines.
- Yext, 6.8M citations: 86% of AI citations come from brand-managed sources; 44% from first-party sites.
- Enrich Labs 2026: comparison content and original-research reports are the two highest-citation B2B content types.
- AI referral traffic is small (~1% of sessions) but converts far better than organic — Ahrefs saw AI visitors at 0.5% of traffic producing 12.1% of signups.
- Structured data doesn't cause citations; it makes you a resolvable entity so an engine will name you. Organization + `@graph` + `sameAs` is the foundational block.
### Agent Skills distribution economics
- ~56,804 indexed SKILL.md directories as of a July 2026 crawl, competing for fewer than 100 reliable auto-trigger slots per agent (arXiv 2608.12610). Publishing for reach doesn't work at this scale; building internally does.

## Appendix B — Writing rules for every note (GEO mechanics, not optional)
- **Answer-first.** First 1–2 sentences of every section answer the heading directly, in 40–60 words. Sections must survive being read in isolation.
- **One claim per heading.** Headings are questions a buyer would actually type.
- **Numbers or delete it.** "Fast sync" → "30-second push cycle." Statistics were the second-biggest measured lift in the KDD study.
- **Cite outward.** Link Tally's XML docs, the Resend API, the OpenRouter model card. Outbound citation correlates with being cited.
- **No adjectives about yourselves.** "Robust", "seamless", "cutting-edge" are anti-signal in both directions.
- **State the boundary.** The `ls-crm` doc already does this well ("Scope of the System" — the office PC must be on). Keep that habit; buyers trust bounded claims and so do retrieval systems.
